## Что это такое?
Представьте завод с десятками датчиков: температура обмотки трансформатора, вибрация подшипника двигателя, давление в насосе. Сейчас кто-то должен заметить на экране — или, того хуже, услышать громкий звук — прежде чем поймёт, что деталь перегревается или вот-вот выйдет из строя.

**Ironpulse непрерывно следит за этими датчиками и сразу сообщает, когда показания выходят за допустимые пределы или начинают вести себя необычно** — теми же статистическими методами, которыми пользуются инженеры предиктивного обслуживания. Жёсткие пределы ловят то, что уже опасно; статистика ловит и резкие скачки, и медленное, ползучее ухудшение — задолго до того, как значение доберётся до предела.

Вы получаете:
- **Живой дашборд** в браузере на 8 языках — текущее значение каждого датчика в его единицах, график с линиями пределов, лента алертов с критичностью.
- **Уведомления** в Telegram, Slack или на любой webhook — на языке вашей команды, включая сообщения о потере связи с устройством и её восстановлении.
- **Историю показаний** на диске — перезапуск не стирает данные, а любой датчик можно выгрузить в CSV за весь срок хранения.
- **API и метрики** для других систем: REST, WebSocket и `/metrics` для Prometheus/Grafana.
- **Защиту доступа** по токену для API, живого потока и метрик.

Система общается с реальным промышленным оборудованием по протоколу **Modbus TCP** — стандарту связи, который используется в огромной доле промышленных датчиков, контроллеров (ПЛК) и счётчиков по всему миру. Ironpulse читает holding- и input-регистры, понимает 16- и 32-битные целые и числа с плавающей точкой с любым порядком слов, применяет масштаб и смещение — то есть работает с картами регистров реальных устройств, а не только с демо.

### Кому это подойдёт?
- **Инженерам и техникам**, которым нужен лёгкий инструмент мониторинга с самостоятельным хостингом — без оплаты (или ожидания одобрения от ИТ-отдела) коммерческой SCADA/IIoT-платформы.
- **Разработчикам**, которые смотрят на исходный код как на пример продакшен-грейд кодовой базы на C++20: асинхронная сеть, собственный WebSocket-сервер, REST API, контейнеризованное развёртывание и настоящий набор тестов — без тяжёлых фреймворков.
- **Студентам и энтузиастам**, которые хотят увидеть, как реально устроен промышленный pipeline мониторинга от начала до конца.

Вам **не обязательно** знать C++, чтобы запустить систему — см. [Быстрый старт](#быстрый-старт) ниже. Docker сам всё соберёт.

## Как это выглядит.
Слева — устройства и их статус связи. В центре — карточка на каждый датчик: название, крупное текущее значение в единицах датчика (красным, если оно за пределом), живой график с пунктирными линиями пределов и кнопка выгрузки CSV. Справа — лента алертов: красные «критично» для выхода за пределы, жёлтые «предупреждение» для статистических аномалий. Всё обновляется в реальном времени, без перезагрузки страницы, и одинаково удобно на большом мониторе диспетчерской и на телефоне.

## Языки интерфейса.
Дашборд и уведомления переведены на 8 языков: **русский** (основной), английский, китайский, хинди, испанский, французский, немецкий и итальянский — переключатель в правом верхнем углу. Это описание тоже есть на всех 8 языках (ссылки — в начале страницы). Язык дашборда выбирается так:
1. параметр `?lang=` в адресе — например, `http://localhost:8080/?lang=en` (удобно, чтобы отправить ссылку коллеге);
2. язык, выбранный ранее в этом браузере;
3. язык браузера, если он поддерживается;
4. иначе — русский.

Язык уведомлений задаётся в конфигурации (`notifications.language`) — см. [Уведомления](#уведомления).

Переводы дашборда лежат в [`web/js/i18n/locales/`](web/js/i18n/locales): чтобы добавить язык, скопируйте `ru.js`, переведите значения и подключите файл в `web/index.html` и в список `supported` в [`web/js/i18n/i18n.js`](web/js/i18n/i18n.js). CI проверяет, что во всех языках одинаковый набор строк.

## Быстрый старт.
Вам нужен установленный [Docker](https://docs.docker.com/get-docker/) — это единственное требование. Docker сам соберёт всё остальное (компилятор C++, все библиотеки) внутри контейнера, так что ваш компьютер останется чистым.
```bash
git clone https://github.com/Anton-Sergeev-EA/Ironpulse.git
cd Ironpulse/deploy/docker
docker compose up --build
```
Дождитесь завершения (пара минут при первом запуске — идёт компиляция C++ из исходников), затем откройте в браузере:
- **http://localhost:8080** — живой дашборд
- **http://localhost:8080/api/v1/sensors** — сырой API, если интересно

Готово. Теперь вы наблюдаете за двумя симулированными устройствами — трансформатором (температура обмотки и масла) и насосом (вибрация подшипника и давление). Симулятор время от времени выдаёт скачки и затяжные отклонения — смотрите, как в панели «Активные алерты» появляются предупреждения и критичные события.

Готовые образы для amd64 и arm64 (Raspberry Pi, ARM-шлюзы) публикуются при каждом релизе:
```bash
docker pull ghcr.io/anton-sergeev-ea/ironpulse:latest
```

### Что-то не работает?
- **Порт уже занят?** Очень частая ситуация, если у вас уже что-то работает на порту 8080 (Jenkins, другой дашборд и т.д.). Скопируйте `.env.example` в `.env` в папке `deploy/docker/`, поменяйте `HTTP_PORT`/`WS_PORT`/`NGINX_PORT` на свободные, и запустите `docker compose up --build` заново. Один файл, одно изменение — больше ничего трогать не нужно.
- **Всё ещё не получается?** Смотрите раздел [Решение проблем](#решение-проблем) ниже.

## Что вы видите на экране и что значат термины.
Если вы не из промышленной/инженерной среды — вот короткий глоссарий того, что на дашборде:

| Термин | Простое объяснение |
|---|---|
| **Modbus** | "Язык" многолетней давности, но всё ещё повсеместно используемый промышленными датчиками и контроллерами для общения с программами. Ironpulse говорит на нём напрямую. |
| **Регистр** | Ячейка памяти устройства, в которой лежит показание. Карта регистров (какой адрес что значит) есть в документации любого Modbus-устройства. |
| **Предел (limit)** | Граница, за которую значение выходить не должно: например, температура обмотки выше 90 °C. Выход за предел — **критичный** алерт. |
| **Аномалия** | Показание, которое не вписывается в недавний нормальный паттерн датчика — может быть резкий скачок, а может быть медленный дрейф, который продолжался слишком долго. Это **предупреждение**: значение ещё в пределах, но ведёт себя необычно. |
| **Уверенность (confidence)** | Насколько система уверена, что отмеченное показание — настоящая аномалия, а не просто шум. Выше — увереннее. |
| **Z-score, EWMA, CUSUM** | Три разных статистических метода обнаружения аномалий, каждый хорош для своего *типа* проблемы (см. [Как работает обнаружение аномалий](#как-работает-обнаружение-аномалий)). Ironpulse запускает несколько сразу и поднимает тревогу только когда они согласны друг с другом — меньше ложных срабатываний. |
| **WAL (write-ahead log, журнал упреждающей записи)** | Страховка: каждое показание сразу сохраняется на диск по мере поступления, так что перезапуск не теряет недавнюю историю. |
| **REST API / WebSocket** | Два способа, которыми другое ПО может получать данные из Ironpulse: REST — "дай мне текущее состояние", WebSocket — "держи меня в курсе в реальном времени". |

## Как работает обнаружение аномалий.
На каждое показание работают два независимых механизма.

**Жёсткие пределы** (`limits`). Значение ниже `low` или выше `high` — критичный алерт. Он срабатывает один раз, когда значение выходит за предел, а не на каждом опросе, пока оно там остаётся; следующий — только после возврата в норму.

**Статистика.** Единый фиксированный порог либо пропускает медленные проблемы (вибрация подшипника, нарастающая днями), либо поднимает ложную тревогу на безобидный шум. Поэтому на каждый датчик можно запустить несколько независимых стратегий и поднимать тревогу только когда достаточное их число (`votes_required`) согласны:
- **Z-score** — отмечает показание, которое отклоняется от недавнего среднего датчика на необычное число стандартных отклонений. Хорошо ловит резкие скачки.
- **EWMA** (экспоненциально взвешенное скользящее среднее) — отслеживает самонастраивающуюся "норму", которая реагирует на настоящие сдвиги быстрее, чем фиксированное окно.
- **CUSUM** (кумулятивная сумма) — накапливает свидетельства *устойчивого* дрейфа, ловя медленную деградацию, которую проверка по одной точке пропустила бы, пока она не станет серьёзной. Ему нужны нормальное среднее (`mean`) и разброс (`stddev`) датчика.

Ещё три детали держат ленту алертов осмысленной, а не шумной:
- **прогрев** — сразу после запуска детекторы молчат, пока не наберут статистику (z-score — половину окна, EWMA — ⌈3/α⌉ точек), иначе каждый перезапуск давал бы ложные тревоги;
- **интервал тишины** (`cooldown_seconds`) — затяжное отклонение даёт одно уведомление, а не одно в секунду;
- **кворум** — одиночный всплеск одного детектора на шумном датчике не будит дежурного.

## Настройка своих устройств.
Устройства и их датчики описываются в конфиге (`deploy/config/config.example.json` для запуска без Docker, `config.docker.json` — для Docker). Пример реального устройства с тремя датчиками:
```json
{
  "devices": [
    {
      "id": "transformer_01",
      "host": "192.168.1.50",
      "port": 502,
      "unit_id": 1,
      "poll_interval_ms": 1000,
      "timeout_ms": 3000,
      "sensors": [
        {
          "id": "winding_temp",
          "name": "Температура обмотки",
          "unit": "°C",
          "register_type": "holding",
          "address": 0,
          "data_type": "float32",
          "word_order": "big",
          "limits": { "high": 90 }
        },
        {
          "id": "oil_temp",
          "name": "Температура масла",
          "unit": "°C",
          "register_type": "input",
          "address": 10,
          "data_type": "int16",
          "scale": 0.1,
          "limits": { "high": 75 },
          "detection": {
            "detectors": [{ "type": "cusum", "mean": 55, "stddev": 0.5 }],
            "cooldown_seconds": 120
          }
        },
        {
          "id": "load_current",
          "name": "Ток нагрузки",
          "unit": "A",
          "address": 20,
          "data_type": "uint32",
          "word_order": "little",
          "scale": 0.01,
          "limits": { "low": 0, "high": 400 }
        }
      ]
    }
  ]
}
```

**Устройство:**

| Поле | По умолчанию | Что это |
|---|---|---|
| `id` | — | Уникальное имя устройства: латиница, цифры, `_`, `-`, `.` |
| `host`, `port` | —, `502` | Где доступно устройство (или шлюз Modbus TCP) |
| `unit_id` | `1` | Адрес Modbus slave/unit (важен за шлюзами RS-485) |
| `poll_interval_ms` | `1000` | Как часто опрашивать. Опрос идёт с фиксированным шагом и не «уплывает», даже если устройство отвечает медленно |
| `timeout_ms` | `3000` | Сколько ждать ответа. Устройство, которое приняло соединение и молчит, будет помечено как недоступное |
| `sensors` | один `uint16` в регистре 0 | Список датчиков устройства |

**Датчик:**

| Поле | По умолчанию | Что это |
|---|---|---|
| `id` | — | Уникальное (среди всех устройств) имя датчика; им же называется файл истории |
| `name`, `unit` | `id`, пусто | Название и единицы для дашборда и уведомлений |
| `register_type` | `holding` | `holding` (функция 0x03) или `input` (0x04) |
| `address` | `0` | Адрес первого регистра (с нуля, как в протоколе) |
| `data_type` | `uint16` | `uint16`, `int16`, `uint32`, `int32`, `float32` (32-битные занимают два регистра) |
| `word_order` | `big` | Для 32-битных: `big` — старшее слово первым (ABCD), `little` — младшее первым (CDAB) |
| `scale`, `offset` | `1`, `0` | Значение = сырое × `scale` + `offset` |
| `limits.low`, `limits.high` | нет | Жёсткие пределы, выход за которые — критичный алерт |
| `detection.detectors` | z-score + EWMA | Список стратегий: `{"type": "zscore", "window": 60, "threshold": 3}`, `{"type": "ewma", "alpha": 0.2, "threshold": 3}`, `{"type": "cusum", "mean": …, "stddev": …, "slack": 0.5, "threshold": 5}`. Пустой список отключает статистику |
| `detection.votes_required` | `1` | Сколько стратегий должны согласиться |
| `detection.cooldown_seconds` | `30` | Минимальный интервал между алертами одного вида по датчику |

Ironpulse сам объединяет соседние регистры одного устройства в как можно меньшее число запросов (до 125 регистров за запрос) — десять датчиков обычно читаются за один-два запроса, а не за десять.

Конфиг проверяется при запуске, и ошибки указывают точное место: например, `config: devices[0].sensors[2].data_type: unknown value 'float64' (expected one of: uint16, int16, uint32, int32, float32)`. Устройства из старых версий конфига (без списка `sensors`) продолжают работать как раньше.

Любое строковое значение может ссылаться на переменную окружения: `"host": "${PLC_HOST}"`. Основные настройки можно переопределить через переменные `IRONPULSE_*` без правки файла — см. [`docs/adr/0003-env-driven-config.md`](docs/adr/0003-env-driven-config.md).

## Уведомления.
Ironpulse отправляет алерты и сообщения о потере связи с устройством в Telegram, Slack и на любой HTTP-адрес (webhook). Тексты — на выбранном языке, с названием датчика, значением, пределом и единицами:
```
🔴 КРИТИЧНО
Температура обмотки: значение 142 °C выше предела 90 °C
Устройство: transformer_01
Время: 2026-10-02 06:54:09 UTC
Дашборд: https://monitoring.example.com
```

Проще всего включить через `.env` (Docker) или переменные окружения:

| Переменная | Что это |
|---|---|
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | Бот из [@BotFather](https://t.me/BotFather), добавленный в ваш чат или группу |
| `SLACK_WEBHOOK_URL` | Incoming Webhook из настроек Slack |
| `WEBHOOK_URL` | Любой адрес, принимающий JSON-POST |
| `NOTIFY_LANGUAGE` | `ru`, `en`, `zh`, `hi`, `es`, `fr`, `de` или `it` |
| `IRONPULSE_PUBLIC_URL` | Адрес дашборда — ссылка на него появится в уведомлениях |

(Без Docker это `IRONPULSE_TELEGRAM_BOT_TOKEN`, `IRONPULSE_TELEGRAM_CHAT_ID`, `IRONPULSE_SLACK_WEBHOOK_URL`, `IRONPULSE_WEBHOOK_URL`, `IRONPULSE_NOTIFY_LANGUAGE`.)

То же самое в конфиге, с дополнительными возможностями:
```json
"notifications": {
  "language": "ru",
  "min_severity": "critical",
  "dashboard_url": "https://monitoring.example.com",
  "channels": [
    { "type": "telegram", "bot_token": "${TG_TOKEN}", "chat_id": "-1001234567890" },
    { "type": "webhook", "url": "https://hooks.example.com/ironpulse",
      "headers": { "Authorization": "Bearer ${HOOK_SECRET}" } }
  ]
}
```
- `min_severity: "critical"` — присылать только выходы за пределы и потерю связи, без статистических предупреждений.
- У Telegram-канала можно указать `url` — адрес собственного Bot API-сервера или прокси, если `api.telegram.org` недоступен из сети предприятия.
- Webhook получает структурированный JSON: `type` (`alert`, `device_offline`, `device_online`), `severity`, `title`, `text`, `timestamp`, `device_id`, `sensor_id` и объект `alert` с полями `kind`, `value`, `limit`, `direction`, `votes` и т.д. — удобно для систем заявок и автоматизации.

Отправка идёт в фоне и не тормозит опрос; при ошибках сервера делается до трёх попыток с растущей паузой. Канал, для которого не заданы адрес или токен, отключается с предупреждением в логе, а не роняет систему.

## Безопасность.
По умолчанию API открыт — это удобно для локального знакомства, но не для сервера в сети. Задайте токен:
```bash
# deploy/docker/.env
IRONPULSE_API_TOKEN=$(openssl rand -hex 32)
```
После этого REST API, живой WebSocket-поток и `/metrics` требуют заголовок `Authorization: Bearer <токен>`. Дашборд один раз спросит токен и запомнит его в браузере. `/healthz` остаётся открытым для health check'ов.

Также из коробки: проверка параметров запросов (`400` вместо падения), ограничение размера входящих WebSocket-кадров и заголовков, отключение «зависших» клиентов, сравнение токена за постоянное время, имена датчиков, безопасные для файловой системы, непривилегированный пользователь в контейнере и изолированный systemd-юнит.

## Мониторинг самого Ironpulse.
`GET /metrics` отдаёт метрики в формате Prometheus — подключите к Prometheus/Grafana или VictoriaMetrics:

| Метрика | Что показывает |
|---|---|
| `ironpulse_sensor_value{sensor,unit}` | Последнее значение каждого датчика |
| `ironpulse_device_up{device}` | 1 — устройство отвечает, 0 — нет |
| `ironpulse_readings_total{sensor}` | Сколько показаний получено |
| `ironpulse_alerts_total{sensor,kind,severity}` | Сколько алертов поднято |
| `ironpulse_poll_errors_total{device}` | Сколько запросов к устройству не удалось |
| `ironpulse_notifications_total{channel,result}` | Доставка уведомлений |
| `ironpulse_websocket_clients`, `ironpulse_uptime_seconds`, `ironpulse_build_info{version}` | Состояние самого сервиса |

```yaml
# prometheus.yml
scrape_configs:
  - job_name: ironpulse
    authorization: { credentials: "<токен>" }   # если задан IRONPULSE_API_TOKEN
    static_configs: [{ targets: ["ironpulse-host:8080"] }]
```

## Выгрузка потока данных.
Кроме дашборда, Ironpulse может записывать каждое показание в компактные двоичные файлы — для озера данных, исторического архива (historian), офлайн-анализа или обучения моделей. Запись на диск идёт в отдельном потоке: медленный или заполненный диск никогда не задержит опрос и алерты — в худшем случае часть показаний не попадёт в выгрузку, и это будет видно в метриках.

```json
"export": { "enabled": true, "directory": "export", "segment_max_mb": 64 }
```

В Docker достаточно `EXPORT_ENABLED=true` в `.env` — файлы появятся в томе данных, в `/app/data/export`.

Файлы `telemetry-<время>-NNNNNN.ipseg`: 24 байта на показание, контрольная сумма CRC-32C на каждый пакет и список датчиков внутри каждого файла, поэтому файл читается сам по себе, даже после изменения конфигурации. Файл, который ещё пишется, заканчивается на `.part` — забирайте только готовые `.ipseg`. Ironpulse их не удаляет: хранение выгрузки — на вашей стороне.

```bash
ironpulse-export verify export/                       # проверить CRC каждого пакета
ironpulse-export dump export/ > readings.csv          # все показания в CSV
ironpulse-export dump --sensor winding_temp export/   # только один датчик
```

Описание формата — [`docs/export-format.md`](docs/export-format.md), читатель на Python без зависимостей — [`tools/export_reader/read_segment.py`](tools/export_reader/read_segment.py), метрики — `ironpulse_export_*` в `/metrics`.

## Варианты развёртывания.
Выберите то, что соответствует вашей ситуации:

| Сценарий | Инструкция |
|---|---|
| Просто хочу посмотреть, как это работает локально | [Быстрый старт](#быстрый-старт) выше |
| Разворачиваю на своём сервере/VDS, больше там ничего не работает | [Docker Compose, отдельный VDS](#docker-compose-отдельный-vds) |
| На сервере уже работают другие сайты со своим nginx + HTTPS | [За уже существующим nginx](#развёртывание-за-уже-существующим-nginx-и-доменом) |
| Docker нельзя, собираю C++ напрямую | [Сборка из исходников](#сборка-из-исходников-без-docker) |

### Docker Compose, отдельный VDS.
Если Ironpulse — единственное, что работает на сервере:
```bash
cd deploy/docker
cp .env.example .env          # задайте IRONPULSE_API_TOKEN и, по желанию, уведомления
docker compose up -d --build
```
Дашборд доступен на `http://<ip-сервера>:8080` (и через nginx на порту 80, который тоже идёт в комплекте). Для настоящего публичного использования поставьте TLS-сертификат — именно об этом следующий раздел, адаптированный под общий сервер.

### Развёртывание за уже существующим nginx (и доменом).
Если на вашем VDS уже размещены другие сайты со своим nginx и TLS-сертификатами (например, через [certbot](https://certbot.eff.org/)), Ironpulse может встроиться как ещё один сайт, а не бороться за порт 80/443:
```bash
cd deploy/docker
cp .env.example .env
# В .env поставьте IRONPULSE_BIND_HOST=127.0.0.1, чтобы ironpulse был
# доступен только с этой машины, а не напрямую из интернета.
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```
Это привязывает порты ironpulse только к `127.0.0.1` и пропускает встроенный сервис nginx (за это отвечает `docker-compose.prod.yml`), так что ваш существующий nginx становится единственной точкой TLS-терминации.
Затем добавьте vhost — [`deploy/nginx/anton-tests.ru.conf`](deploy/nginx/anton-tests.ru.conf) готовый пример; скопируйте его и подставьте свой домен и пути к сертификату:
```bash
sudo cp deploy/nginx/anton-tests.ru.conf /etc/nginx/sites-available/your-domain.tld
sudo ln -s /etc/nginx/sites-available/your-domain.tld /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

> **Почему отдельная переменная `IRONPULSE_BIND_HOST`, а не просто два Compose-файла с разными `ports:`?** Новые версии Docker Compose объединяют (склеивают) списковые ключи вроде `ports:` между `-f`-файлами вместо того, чтобы заменять их — если оба файла объявляют `ports:` для одного сервиса, они могут незаметно попытаться забиндить один и тот же порт дважды. Пропуская адрес привязки через одну переменную, читаемую прямо в базовом файле, эта проблема исключается полностью. Подробности — в [`docs/adr/0003-env-driven-config.md`](docs/adr/0003-env-driven-config.md).

### Чек-лист перед продакшеном.
Прежде чем направить реальный домен на реальное развёртывание:
- [ ] Задан `IRONPULSE_API_TOKEN` (длинный, случайный: `openssl rand -hex 32`)
- [ ] `IRONPULSE_BIND_HOST=127.0.0.1` выставлен, если спереди стоит reverse proxy (не открывайте сырой порт приложения в интернет напрямую)
- [ ] TLS-сертификат валиден и автоматически продлевается (`certbot renew --dry-run`)
- [ ] `persistence_enabled: true` в конфиге, если важно пережить перезапуск (см. [`deploy/config/config.docker.json`](deploy/config/config.docker.json))
- [ ] `retention_hours` выставлен разумно под размер вашего диска — около 16 байт на показание; старые записи удаляются автоматически раз в час
- [ ] Список `devices` указывает на ваши **реальные** Modbus-устройства, а не на встроенный симулятор, и у каждого датчика заданы `limits`
- [ ] Уведомления проверены: временно опустите предел ниже текущего значения и убедитесь, что сообщение пришло
- [ ] Проверен запас места на диске — сборка Docker временно требует ~3-4 ГБ, хотя финальный образ меньше 250 МБ (`docker builder prune` после успешной сборки освобождает это место)
- [ ] Все health check'и зелёные: `docker compose ps` показывает каждый сервис как `healthy`

### Сборка из исходников (без Docker).
Нужен компилятор C++20 (GCC ≥ 12 или Clang ≥ 15), CMake ≥ 3.20, Ninja и OpenSSL ≥ 3 (`libssl-dev` — для уведомлений по HTTPS). Всё остальное (Asio, spdlog, nlohmann/json, cpp-httplib, Catch2) подтягивается автоматически.

```bash
cmake --preset debug
cmake --build --preset debug -j$(nproc)
ctest --preset debug --output-on-failure
```

Другие пресеты: `release`, `asan` (AddressSanitizer + UBSan), `tsan` (ThreadSanitizer).

Чтобы реально запустить систему, нужны Modbus-устройства для опроса — используйте встроенный симулятор для самодостаточной демонстрации:
```bash
pip install -r tools/modbus_simulator/requirements.txt --break-system-packages
python3 tools/modbus_simulator/simulator.py --port 5020 &

./build/debug/ironpulse deploy/config/config.example.json
```

`ironpulse --version` печатает версию. См. [`deploy/systemd/ironpulse.service`](deploy/systemd/ironpulse.service) для защищённого systemd-юнита, если разворачиваете именно так на VDS; секреты он читает из `/etc/ironpulse/ironpulse.env`.

## Решение проблем.
**"Port is already allocated" при запуске Docker.**
Что-то ещё на вашей машине использует этот порт. Либо остановите это, либо поменяйте порт в `.env` (см. [Быстрый старт](#быстрый-старт)). Если Docker настаивает, что порт занят, но вы не можете найти, что его использует, попробуйте `docker builder prune -af` и перезапуск демона Docker — частично неудавшийся предыдущий контейнер может оставить внутреннее состояние Docker в запутанном виде.

**Ironpulse не запускается и пишет `Failed to load config ... config: devices[0]...`.**
Ошибка в конфиге — в сообщении указано точное поле и что с ним не так. Исправьте его и запустите снова.

**Дашборд просит токен, а я его не задавал.**
Значит, токен задан в окружении (`IRONPULSE_API_TOKEN` в `.env` или `api_token` в конфиге). Введите его — или удалите, если доступ должен быть открытым.

**Дашборд загружается, но графики остаются пустыми / "Chart is not defined" в консоли браузера.**
Не должно происходить — Chart.js идёт встроенным в `web/js/vendor/`, а не загружается с CDN, специально для того, чтобы это не могло случиться даже в ограниченных сетях. Если всё же видите это — браузер загружает устаревшую закэшированную копию страницы: жёсткое обновление через `Ctrl+Shift+R`.

**Устройство показывает "не в сети", а в логе `device unreachable: cannot connect`.**
Ironpulse не может достучаться до устройства по указанным `host`/`port`. Если используете Docker Compose, проверьте, что значение `host` устройства совпадает с именем сервиса Docker (например, `simulator`), а не `127.0.0.1` — контейнеры не могут обращаться друг к другу через `localhost`.

**В логе `poll failed: device exception code 2`.**
Устройство отвечает, но отказывается отдать запрошенные регистры: код 2 — «неверный адрес». Сверьте `address`, `register_type` и `data_type` с картой регистров устройства (часто путают нумерацию с нуля и с единицы, или holding и input).

**Значения выглядят как мусор (огромные числа, отрицательные вместо положительных).**
Почти всегда это `data_type` или `word_order`: попробуйте `word_order: "little"` для 32-битных значений, `int16` вместо `uint16` для величин, которые бывают отрицательными, и проверьте `scale`.

**Уведомления не приходят.**
Смотрите лог: `Notification via telegram failed (HTTP 401)` — неверный токен бота; `HTTP 400` — неверный `chat_id` или бот не добавлен в чат; `network error` — сервер не видит интернет (для Telegram можно указать прокси или собственный Bot API-сервер в `url` канала). Метрика `ironpulse_notifications_total{result="error"}` покажет, сколько доставок не удалось.

**`Modbus resolve failed... Host not found`.**
Проблема с DNS/сетью внутри Docker — обычно решается сама в течение нескольких секунд, пока сеть контейнера завершает инициализацию. Если сохраняется — `docker compose down && docker compose up -d --build`, чтобы пересоздать сеть с чистого листа.

**Поменял файл, но Docker всё ещё отдаёт старую версию.**
Docker агрессивно кэширует слои сборки. Заставьте пересобрать без кэша: `docker compose build --no-cache`, и если этого недостаточно — сначала `docker builder prune -af`, чтобы полностью очистить все закэшированные слои.

**Я на VDS с ограниченным местом на диске.**
См. [чек-лист перед продакшеном](#чек-лист-перед-продакшеном) выше — сборке временно нужно больше места, чем занимает финальный образ. `docker builder prune` после успешной сборки.

## Архитектура (для разработчиков).
```
Modbus TCP устройства → protocol (опрос, декодирование регистров) → EventBus
                                                                       │
              ┌──────────────────────┬───────────────────────┬─────────┴──────────┐
              ▼                      ▼                       ▼                    ▼
   storage (ring buffer + WAL)   analytics (пределы,     api (REST, WebSocket,   metrics
                                 детекторы, кворум)      /metrics) → дашборд
                                         │
                                         ▼
                                 notify (Telegram, Slack, webhook)
```

Каждый слой (`core`, `protocol`, `storage`, `ingest`, `analytics`, `api`, `notify`) — независимый CMake-таргет со своими тестами, поэтому его можно собирать, тестировать и бенчить изолированно. Слои общаются через `EventBus`, а не напрямую. См. [`docs/architecture.md`](docs/architecture.md) для модели конкурентности и обоснования решений, и [`docs/adr/`](docs/adr/) для конкретных решений (почему Asio, почему WAL, почему конфигурация через env-переменные).

```
include/ironpulse/        Публичные заголовки, по подкаталогу на слой
src/                      Реализация, зеркалит include/ + main.cpp
tests/unit/               Catch2 unit-тесты, по файлу на компонент
tests/integration/        Сквозные тесты: поддельное Modbus-устройство → алерт
tests/benchmarks/         Google Benchmark сьют
tools/modbus_simulator/   Эмулятор устройств на Python для демо/тестов
web/                      Статический дашборд (vanilla JS + встроенный Chart.js), 8 языков
deploy/docker/            Dockerfile, docker-compose.yml, .env.example
deploy/nginx/             Шаблоны reverse-proxy для nginx
deploy/systemd/           Unit-файл для развёртывания на голом VDS
docs/                     Архитектура, OpenAPI, ADR
```

### Справочник по API.
Полное описание — [`docs/openapi.yaml`](docs/openapi.yaml) (OpenAPI 3; откройте в Swagger UI или импортируйте в Postman).

| Эндпоинт | Описание |
|---|---|
| `GET /api/v1/devices` | Устройства: `id`, `online`, `poll_interval_ms`, список датчиков |
| `GET /api/v1/sensors` | Датчики: `id`, `name`, `unit`, `device_id`, `limits`, последнее значение |
| `GET /api/v1/series/{sensor_id}?since=<секунды>` | История за указанный период (по умолчанию 300 с; с WAL — за весь срок хранения). Длинные периоды прореживаются до 10 000 точек |
| `GET /api/v1/series/{sensor_id}?since=<секунды>&format=csv` | То же в CSV, без прореживания — для Excel и анализа |
| `GET /api/v1/alerts?limit=<n>` | Недавние алерты, сначала новые (1–1000, по умолчанию 50): `kind`, `severity`, `value`, `limit`, `direction`, `votes`, `detectors_total`, `confidence` |
| `GET /api/v1/config` | `ws_port`, `ws_host`, `auth_required`, `version` — всё, что нужно дашборду для старта (не требует токена) |
| `GET /metrics` | Метрики Prometheus |
| `GET /healthz` | Проверка живости и версия (не требует токена) |
| `WS /live` (через `/ws/live` за reverse proxy) | Живой push: события `reading`, `anomaly`, `device_status`. С токеном — `?token=<токен>` |

### Инженерные практики.
- Строгие предупреждения компилятора (`-Wall -Wextra -Wpedantic -Wconversion ...`), сборка без единого предупреждения; опционально — как ошибки (`IRONPULSE_WARNINGS_AS_ERRORS`)
- 131 тест: unit-тесты каждого компонента, тесты HTTP API и WebSocket-рукопожатия на реальных сокетах, сквозные тесты с поддельным Modbus-устройством по TCP (декодирование, пределы, тайм-ауты, потеря и восстановление связи). Все зелёные под AddressSanitizer/UndefinedBehaviorSanitizer и ThreadSanitizer
- CI-матрица по GCC и Clang, санитайзеры, `clang-format`, `ruff` для симулятора, проверка полноты переводов, сборка Docker и smoke-тест Compose с проверкой живых данных — всё в [`.github/workflows/ci.yml`](.github/workflows/ci.yml)
- Релизы по тегу: нативная сборка образов под amd64 и arm64 и публикация в GitHub Container Registry — [`.github/workflows/release.yml`](.github/workflows/release.yml)
- Многостадийная сборка Docker (тулчейн компилятора никогда не попадает в runtime-образ), непривилегированный пользователь контейнера, health check на каждом сервисе, чистый build-контекст через `.dockerignore`
- У дашборда ноль внешних runtime-зависимостей — Chart.js встроен, а не грузится с CDN, поэтому работает в ограниченных или офлайн-сетях
