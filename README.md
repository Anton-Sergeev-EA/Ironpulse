# Ironpulse.

**Система промышленного мониторинга в реальном времени, которая следит за показаниями датчиков вашего оборудования и предупреждает, когда что-то пошло не так — до того, как оно сломается.**

## Что это такое?
Представьте завод с десятками датчиков: температура обмотки трансформатора, вибрация подшипника двигателя, давление в насосе. Сейчас кто-то должен заметить на экране — или, того хуже, услышать громкий звук — прежде чем поймёт, что деталь перегревается или вот-вот выйдет из строя.
**Ironpulse непрерывно следит за этими датчиками и автоматически отмечает показания, которые выглядят ненормально** — теми же статистическими методами, которыми пользуются инженеры предиктивного обслуживания. Не просто "температура выше 80°C = тревога" (это пропускает медленные проблемы и поднимает ложную тревогу на обычные всплески), а распознавание паттернов, которое ловит и резкие скачки, и медленное, ползучее ухудшение.
Вы получаете:
- **Живой дашборд** в браузере — текущие показания каждого датчика, график в реальном времени, лента обнаруженных аномалий.
- **API**, из которого другие системы (корпоративный дашборд, бот в Slack, система заявок на обслуживание) могут забирать данные.
- **Историю показаний**, сохранённую на диск — перезапуск сервера не стирает последние дни данных.
Система общается с реальным промышленным оборудованием по протоколу **Modbus TCP** — стандарту связи, который используется в огромной доле промышленных датчиков, контроллеров (ПЛК) и устройств по всему миру. Если ваше оборудование "говорит" на Modbus — Ironpulse сможет его слушать.

### Кому это подойдёт?
- **Инженерам и техникам**, которым нужен лёгкий инструмент мониторинга с самостоятельным хостингом — без оплаты (или ожидания одобрения от ИТ-отдела) коммерческой SCADA/IIoT-платформы.
- **Разработчикам**, которые смотрят на исходный код как на пример продакшен-грейд кодовой базы на C++20: асинхронная сеть, собственный WebSocket-сервер, REST API, контейнеризованное развёртывание и настоящий набор тестов — без тяжёлых фреймворков.
- **Студентам и энтузиастам**, которые хотят увидеть, как реально устроен промышленный pipeline мониторинга от начала до конца.
Вам **не обязательно** знать C++, чтобы запустить систему — см. [Быстрый старт](#быстрый-старт-5-минут-с-docker) ниже. Docker сам всё соберёт.

## Как это выглядит.
После запуска дашборд выглядит так: список устройств слева (статус online/offline), живые обновляющиеся графики в центре, и лента обнаруженных аномалий справа — всё обновляется в реальном времени по мере поступления показаний, без перезагрузки страницы.

## Быстрый старт.
Вам нужен установленный [Docker](https://docs.docker.com/get-docker/) — это единственное требование. Docker сам соберёт всё остальное (компилятор C++, все библиотеки) внутри контейнера, так что ваш компьютер останется чистым.
```bash
git clone https://github.com/Anton-Sergeev-EA/ironpulse.git
cd ironpulse/deploy/docker
docker compose up --build
```
Дождитесь завершения (пара минут при первом запуске — идёт компиляция C++ из исходников), затем откройте в браузере:
- **http://localhost:8080** — живой дашборд
- **http://localhost:8080/api/v1/devices** — сырой API, если интересно
Готово. Теперь вы наблюдаете за двумя симулированными датчиками (температура трансформатора и вибрация подшипника), которые время от времени выдают всплески, демонстрируя обнаружение аномалий — смотрите за появлением записей в панели "Активные алерты".

### Что-то не работает?
- **Порт уже занят?** Очень частая ситуация, если у вас уже что-то работает на порту 8080 (Jenkins, другой дашборд и т.д.). Скопируйте `.env.example` в `.env` в папке `deploy/docker/`, поменяйте `HTTP_PORT`/`WS_PORT`/`NGINX_PORT` на свободные, и запустите `docker compose up --build` заново. Один файл, одно изменение — больше ничего трогать не нужно.
- **Всё ещё не получается?** Смотрите раздел [Решение проблем](#решение-проблем) ниже.

## Что вы видите на экране и что значат термины.
Если вы не из промышленной/инженерной среды — вот короткий глоссарий того, что на дашборде:

| Термин                              | Простое объяснение |

| **Modbus**                          | "Язык" многолетней давности, но всё ещё повсеместно используемый промышленными датчиками и контроллерами для общения с программами. Ironpulse говорит на нём напрямую. |
| **Аномалия**                        | Показание, которое не вписывается в недавний нормальный паттерн датчика — может быть резкий скачок, а может быть медленный дрейф, который продолжался слишком долго. |
| **Уверенность (confidence)**        | Насколько система уверена, что отмеченное показание — настоящая аномалия, а не просто шум. Выше — увереннее. |
| **Z-score, EWMA, CUSUM**            | Три разных статистических метода обнаружения аномалий, каждый хорош для своего *типа* проблемы (см. [Как работает обнаружение аномалий](#как-работает-обнаружение-аномалий)). Ironpulse запускает несколько сразу и поднимает тревогу только когда они согласны друг с другом — меньше ложных срабатываний. |
| **WAL (write-ahead log, журнал упреждающей записи)** | Страховка: каждое показание сразу сохраняется на диск по мере поступления, так что перезапуск не теряет недавнюю историю. |
| **REST API / WebSocket**             | Два способа, которыми другое ПО может получать данные из Ironpulse: REST — "дай мне текущее состояние", WebSocket — "держи меня в курсе в реальном времени". |

## Как работает обнаружение аномалий.
Ironpulse не просто проверяет "это число слишком большое?" — единый фиксированный порог либо пропускает медленные проблемы (вибрация подшипника, нарастающая днями), либо поднимает ложную тревогу на безобидный шум. Вместо этого система запускает до трёх независимых стратегий обнаружения на каждый датчик и поднимает тревогу только когда достаточное число из них согласны:
- **Z-score** — отмечает показание, которое отклоняется от недавнего среднего датчика на необычное число стандартных отклонений. Хорошо ловит резкие скачки.
- **EWMA** (экспоненциально взвешенное скользящее среднее) — отслеживает самонастраивающуюся "норму", которая реагирует на настоящие сдвиги быстрее, чем фиксированное окно.
- **CUSUM** (кумулятивная сумма) — накапливает свидетельства *устойчивого* дрейфа, ловя медленную деградацию, которую проверка по одной точке пропустила бы, пока она не станет серьёзной.
Этот принцип "сначала голосование, потом тревога" (см. `RuleEngine` в исходном коде) — то, что удерживает ленту алертов осмысленной, а не шумной.

### Docker Compose, отдельный VDS.
Если Ironpulse — единственное, что работает на сервере:
```bash
cd deploy/docker
cp .env.example .env          # редактируйте, только если порт уже занят
docker compose up -d --build
```
Дашборд доступен на `http://<ip-сервера>:8080` (и через nginx на порту 80, который тоже идёт в комплекте). Для настоящего публичного использования поставьте TLS-сертификат — именно об этом следующий раздел, адаптированный под общий сервер.

### Развёртывание за уже существующим nginx (и доменом).
Если на вашем VDS уже размещены другие сайты со своим nginx и TLS-сертификатами (например, через [certbot](https://certbot.eff.org/)), Ironpulse может встроиться как ещё один сайт, а не бороться за порт 80/443:
```bash
cd deploy/docker
cp .env.example .env
# В .env поставьте IRONPULSE_BIND_HOST=127.0.0.1, чтобы ironpulse был
# доступен только с этой машины, а не напрямую из интернета.
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```
Это привязывает порты ironpulse только к `127.0.0.1` и пропускает встроенный сервис nginx (за это отвечает `docker-compose.prod.yml`), так что ваш существующий nginx становится единственной точкой TLS-терминации.
Затем добавьте vhost — [`deploy/nginx/anton-tests.ru.conf`](deploy/nginx/anton-tests.ru.conf) готовый пример; скопируйте его и подставьте свой домен и пути к сертификату:
```bash
sudo cp deploy/nginx/anton-tests.ru.conf /etc/nginx/sites-available/your-domain.tld
sudo ln -s /etc/nginx/sites-available/your-domain.tld /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

> **Почему отдельная переменная `IRONPULSE_BIND_HOST`, а не просто два Compose-файла с разными `ports:`?** Новые версии Docker Compose объединяют (склеивают) списковые ключи вроде `ports:` между `-f`-файлами вместо того, чтобы заменять их — если оба файла объявляют `ports:` для одного сервиса, они могут незаметно попытаться забиндить один и тот же порт дважды. Пропуская адрес привязки через одну переменную, читаемую прямо в базовом файле, эта проблема исключается полностью. Подробности — в [`docs/adr/0003-env-driven-config.md`](docs/adr/0003-env-driven-config.md).

### Чек-лист перед продакшеном.
Прежде чем направить реальный домен на реальное развёртывание:
- [ ] `IRONPULSE_BIND_HOST=127.0.0.1` выставлен, если спереди стоит reverse proxy (не открывайте сырой порт приложения в интернет напрямую)
- [ ] TLS-сертификат валиден и автоматически продлевается (`certbot renew --dry-run`)
- [ ] `persistence_enabled: true` в конфиге, если важно пережить перезапуск (см. [`deploy/config/config.docker.json`](deploy/config/config.docker.json))
- [ ] `retention_hours` выставлен разумно под размер вашего диска — WAL-файлы растут с каждым показанием
- [ ] Список `devices` в `deploy/config/config.docker.json` указывает на ваши **реальные** Modbus-устройства, а не на встроенный симулятор, перед реальным запуском
- [ ] Проверен запас места на диске — сборка Docker временно требует ~3-4 ГБ, хотя финальный образ меньше 250 МБ (`docker builder prune` после успешной сборки освобождает это место)
- [ ] Все health check'и зелёные: `docker compose ps` показывает каждый сервис как `healthy`

### Сборка из исходников (без Docker).
Нужен компилятор C++20 (GCC ≥ 12 или Clang ≥ 15), CMake ≥ 3.20 и Ninja. Всё остальное (Asio, spdlog, nlohmann/json, cpp-httplib, Catch2) подтягивается автоматически.

```bash
cmake --preset debug
cmake --build --preset debug -j$(nproc)
ctest --preset debug --output-on-failure
```

Другие пресеты: `release`, `asan` (AddressSanitizer + UBSan), `tsan` (ThreadSanitizer).

Чтобы реально запустить систему, нужны Modbus-устройства для опроса — используйте встроенный симулятор для самодостаточной демонстрации:
```bash
pip install -r tools/modbus_simulator/requirements.txt --break-system-packages
python3 tools/modbus_simulator/simulator.py --port 5020 &

./build/debug/ironpulse deploy/config/config.example.json
```

См. [`deploy/systemd/ironpulse.service`](deploy/systemd/ironpulse.service) для защищённого systemd-юнита, если разворачиваете именно так на VDS.

## Настройка своих устройств.
Направьте Ironpulse на реальное оборудование, отредактировав список `devices` в вашем конфиге (`deploy/config/config.example.json` или `config.docker.json`):
```json
{
  "devices": [
    {
      "id": "transformer_temp_01",
      "host": "192.168.1.50",
      "port": 502,
      "unit_id": 1,
      "poll_interval_ms": 1000
    }
  ]
}
```

- `host`/`port` — где доступно устройство (стандартный порт Modbus TCP — 502).
- `unit_id` — адрес Modbus slave/unit, если ваше устройство его использует.
- `poll_interval_ms` — как часто опрашивать. Более частый опрос даёт более тонкую детализацию, но создаёт большую нагрузку на устройство и сеть.

Любую настройку можно также переопределить через переменные окружения `IRONPULSE_*` без правки файла — см. [`docs/adr/0003-env-driven-config.md`](docs/adr/0003-env-driven-config.md).

## Решение проблем.
**"Port is already allocated" при запуске Docker.**
Что-то ещё на вашей машине использует этот порт. Либо остановите это, либо поменяйте порт в `.env` (см. [Быстрый старт](#быстрый-старт-5-минут-с-docker)). Если Docker настаивает, что порт занят, но вы не можете найти, что его использует, попробуйте `docker builder prune -af` и перезапуск демона Docker — частично неудавшийся предыдущий контейнер может оставить внутреннее состояние Docker в запутанном виде.

**Дашборд загружается, но графики остаются пустыми / "Chart is not defined" в консоли браузера.**
Не должно происходить — Chart.js идёт встроенным в `web/js/vendor/`, а не загружается с CDN, специально для того, чтобы это не могло случиться даже в ограниченных сетях. Если всё же видите это — браузер загружает устаревшую закэшированную копию страницы: жёсткое обновление через `Ctrl+Shift+R`.

**Устройство показывает "offline", а в логах `Modbus connect failed` / `Connection refused`.**
Ironpulse не может достучаться до устройства по указанным `host`/`port`. Если используете Docker Compose, проверьте, что значение `host` устройства совпадает с именем сервиса Docker (например, `simulator`), а не `127.0.0.1` — контейнеры не могут обращаться друг к другу через `localhost`.

**`Modbus resolve failed... Host not found`.**
Проблема с DNS/сетью внутри Docker — обычно решается сама в течение нескольких секунд, пока сеть контейнера завершает инициализацию. Если сохраняется — `docker compose down && docker compose up -d --build`, чтобы пересоздать сеть с чистого листа.

**Поменял файл, но Docker всё ещё отдаёт старую версию.**
Docker агрессивно кэширует слои сборки. Заставьте пересобрать без кэша: `docker compose build --no-cache`, и если этого недостаточно — сначала `docker builder prune -af`, чтобы полностью очистить все закэшированные слои.

**Я на VDS с ограниченным местом на диске.**
См. [чек-лист перед продакшеном](#чек-лист-перед-продакшеном) выше — сборке временно нужно больше места, чем занимает финальный образ. `docker builder prune` после успешной сборки.

## Архитектура (для разработчиков).
```
Modbus TCP устройства → protocol (async client) → storage (ring buffer + WAL)
                                                          │
                                                          ▼
                                              analytics (обнаружение аномалий)
                                                          │
                                                          ▼
                                        api (REST + WebSocket) → веб-дашборд
```

Каждый слой (`protocol`, `storage`, `analytics`, `api`, `core`) — независимый CMake-таргет со своими unit-тестами, поэтому его можно собирать, тестировать и бенчить изолированно. См. [`docs/architecture.md`](docs/architecture.md) для модели конкурентности и обоснования решений, и [`docs/adr/`](docs/adr/) для конкретных решений (почему Asio, почему WAL, почему конфигурация через env-переменные).

```
include/ironpulse/       Публичные заголовки, по подкаталогу на слой
src/                       Реализация, зеркалит include/ + main.cpp
tests/unit/                Catch2 unit-тесты, по файлу на компонент
tests/benchmarks/           Google Benchmark сьют
tools/modbus_simulator/     Эмулятор устройств на Python для демо/тестов
web/                          Статический дашборд (vanilla JS + встроенный Chart.js)
deploy/docker/                  Dockerfile, docker-compose.yml, .env.example
deploy/nginx/                     Шаблоны reverse-proxy для nginx
deploy/systemd/                    Unit-файл для развёртывания на голом VDS
docs/adr/                          Architecture Decision Records
```

### Справочник по API.
| Эндпоинт | Описание |
|---|---|
| `GET /api/v1/devices` | `[{ "id": ..., "online": bool }, ...]` |
| `GET /api/v1/series/{sensor_id}?since=<секунды>` | Недавние показания, по умолчанию последние 300с |
| `GET /api/v1/alerts?limit=<n>` | Недавние аномалии, сначала новые, по умолчанию 50 |
| `GET /api/v1/config` | `{ "ws_port": ..., "ws_host": ... }` — позволяет дашборду найти WebSocket-сервер без жёстко зашитого порта |
| `GET /healthz` | Проверка живости (используется Docker health check'ами) |
| `WS /live` (через `/ws/live` за reverse proxy) | Живой push: события `reading`, `anomaly`, `device_status` |

### Инженерные практики.
- Строгие предупреждения компилятора (`-Wall -Wextra -Wpedantic -Wconversion ...`), опционально как ошибки (`IRONPULSE_WARNINGS_AS_ERRORS`)
- CI-матрица по GCC и Clang, плюс отдельные джобы ASan/UBSan и ThreadSanitizer, проверка `clang-format` и сборка Docker + smoke-тест Compose — всё в [`.github/workflows/ci.yml`](.github/workflows/ci.yml)
- Многостадийная сборка Docker (тулчейн компилятора никогда не попадает в runtime-образ), непривилегированный пользователь контейнера, health check на каждом сервисе, чистый build-контекст через `.dockerignore`
- У дашборда ноль внешних runtime-зависимостей — Chart.js встроен, а не грузится с CDN, поэтому работает в ограниченных или офлайн-сетях
- 44 unit-теста покрывают каждый компонент, все зелёные под AddressSanitizer/UndefinedBehaviorSanitizer

## Как внести вклад.
Issues и pull request'ы приветствуются. Перед тем как открыть PR:
```bash
cmake --preset debug && cmake --build --preset debug -j$(nproc)
ctest --preset debug --output-on-failure
find include src tests -name '*.cpp' -o -name '*.hpp' | xargs clang-format --dry-run --Werror
```

CI прогоняет те же проверки (плюс санитайзеры и сборку Docker) на каждый pull request.
